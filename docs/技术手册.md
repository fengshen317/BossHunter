# BossHunter 技术手册

> 适用版本：BossHunter 2.0  
> 面向对象：维护者、贡献者和部署人员  
> 核心目标：在不削弱人工确认、频率控制和隐私边界的前提下维护系统

相关文档：[文档中心](README.md) · [安装与升级](安装与升级指南.md) · [配置参考](配置参考.md) · [发布检查清单](GitHub发布检查清单.md)

## 1. 产品与开发边界

BossHunter 的稳定目标是完成以下闭环：

```text
岗位采集 → 规则预筛 → AI 深度评分 → 招呼语生成 → 人工确认
        → 低频发送 → 回复监测 → 建议回复/定制简历 → 人工处理
```

项目不是通用招聘 SaaS、绕过平台控制的自动化框架，也不是无限扩展的通用 Agent 平台。以下能力属于固定安全边界：

- 所有投递和敏感动作必须保留人工确认。
- 不提高默认发送频率，不规避检测，不绕过平台安全机制。
- 不采集、上传或外发用户隐私和登录凭据。
- 不自动点击简历请求卡片的同意、拒绝或发送动作。
- 不允许不受控后台线程或多个高风险任务并行。
- 不硬编码兼容 AI 服务的内部名称、域名或密钥。

## 4. 核心调用关系

```text
CLI / Web API
    │
    ├── Config + Database
    │
    ├── Pipeline / WorkbenchTaskRunner
    │       ├── Scraper ── RuntimeClient ── Node CDP Proxy ── Chrome/Edge
    │       ├── Prefilter / Scorer / Greeter / Resume ── AI Provider
    │       ├── Confirmation UI
    │       └── Sender / Monitor ── Throttle + RuntimeClient
    │
    └── History / Events / Artifacts
```

浏览器层的 Python 代码不直接承担复杂页面自动化，而是通过本地 HTTP 门面调用 `browser/runtime/cdp-proxy.mjs`。运行时 `.mjs` 和 `site-patterns/*.md` 已声明为 wheel artifacts，发布检查必须验证它们存在。

## 4.1 问答 Agent 总体架构

Web 工作台中的问答助手不是单次 Prompt 调用，而是一套基于 LangGraph 的受控通用 Agent。它负责理解用户目标、检索可用能力、规划多步骤任务、执行只读工具、生成审批提案，并把全过程以事件流和运行记录保存下来。

更完整的设计背景、迁移阶段和评测建议见 [受控通用 Agent 架构设计](通用Agent架构设计.md)，生产组件部署见 [Agent 生产基础设施](生产基础设施重构.md)。本节描述当前代码应保持的实现基线。

核心设计原则：

> 查询、研究、分析、比较和内容生成可以自主执行；写库、启动任务、发送消息和其他外部副作用必须进入确定性审批流程。

```text
React 问答页
   │ POST message / SSE stream
   ▼
AssistantService
   ├── 会话锁与 Run 创建
   ├── Token / ExecutionEvent 回调
   └── LangGraph checkpoint 恢复
          │
          ▼
┌──────────────────────────────────────────────────────────────┐
│ Context Resolver → Goal Extractor → Ambiguity Checker       │
│                                  │                           │
│                 ┌────────────────┼────────────────┐          │
│                 ▼                ▼                ▼          │
│            Clarification    Direct Answer     Planner        │
│                                                 │             │
│                                 Plan Evaluator ↔ Replanner    │
│                                                 │             │
│                                      Capability Matcher      │
│                                         │            │        │
│                                  Read-only DAG    ReAct Loop  │
│                                         └─────┬──────┘        │
│                                               ▼               │
│                                      Execution Engine         │
│                                         │            │        │
│                                      Response      Approval   │
│                                                       │       │
│                                             Result Processor  │
└──────────────────────────────────────────────────────────────┘
          │
          ├── PostgreSQL：会话、消息、Checkpoint、Run、步骤、Observation、审批
          ├── Redis：会话锁、取消信号、实时事件
          └── Artifact Store：大结果和生成制品
```

### 4.1.1 分层职责

| 层 | 主要模块 | 职责 |
|---|---|---|
| API 与应用服务 | `web/server.py`、`assistant/service.py` | 会话 API、SSE、运行创建、锁、取消、恢复和结果落库 |
| 上下文层 | `answer_context.py`、`repository.py` | 最近消息、当前岗位、会话摘要、长期记忆和紧凑回答上下文 |
| 理解层 | `understanding.py`、`goal_understanding.py` | 解析意图、交互模式、实体、约束、成功标准和未知项 |
| 决策层 | `routing.py`、`capability_retriever.py`、`capabilities.py` | 决定直接回答、澄清、能力执行或规划，并召回候选能力 |
| 规划层 | `planning.py`、`dag_scheduler.py` | 构建、验证、重建和有界并行执行依赖图 |
| 自主执行层 | `react.py`、`graph.py` | 逐步选择只读工具，记录观察，根据结果继续或结束 |
| 策略与审批层 | `policy.py`、`graph.py` | 应用用户否定约束，按副作用分类拦截动作，生成审批提案 |
| 能力实现层 | `sql_tool.py`、`company_research.py`、`deep_research.py`、`web_search.py` | 查询岗位、研究公司、读取公开信息和生成分析材料 |
| 状态与审计层 | `models.py`、`observations.py`、`execution_events.py` | 定义稳定数据契约，标准化工具结果和执行事件 |
| 基础设施层 | `infrastructure/` | Run、DAG、Observation、审批、制品、分布式锁和取消信号 |

### 4.1.2 LangGraph 节点流程

`assistant/graph.py` 注册以下节点：

1. `context_resolver`：读取最近消息、当前岗位、Web 开关和待审批上下文。
2. `goal_extractor`：把自然语言转换为 `IntentResult` 与 `GoalState`。
3. `ambiguity_checker`：只在缺失信息会实质改变结果时要求澄清。
4. `planner`：仅为复杂、多交付物或有依赖关系的任务建立计划。
5. `plan_evaluator`：检查能力是否存在、依赖是否合法以及审批边界是否正确。
6. `replanner`：计划无效时有限次数重建，禁止无限重规划。
7. `capability_matcher`：将目标、实体和约束映射成能力及标准参数。
8. `dag_executor`：并行执行复杂的无副作用能力。
9. `react_agent` / `react_tool`：简单或探索式问题采用“选择工具 → 观察 → 再判断”循环。
10. `execution_engine`：汇总事实、生成回答或构造待审批动作。
11. `approval`：通过 LangGraph interrupt 暂停，等待用户确认、修改或取消。
12. `result_processor`：审批后使用固定执行器处理，并记录最终结果。

典型路由：

```text
简单知识问答：理解 → 直接回答 → 结束
信息不完整：理解 → 澄清 → 结束，等待下一轮输入
简单数据查询：理解 → 能力匹配 → ReAct → 回答
复杂研究任务：理解 → 规划 → 评估 → 只读 DAG → 综合回答
发送或写入：理解 → 能力匹配/规划 → 生成提案 → 人工审批 → 固定执行器
```

### 4.1.3 状态与数据契约

Agent 的共享契约集中在 `assistant/models.py`：

- `IntentResult`：目标、有限意图类型、实体、约束、缺失字段、置信度、风险和结构化步骤。
- `GoalState`：用户请求、成功标准、约束、假设、未知项和选中的岗位。
- `CapabilitySpec`：能力说明、工具名、输入输出 Schema、风险、副作用、审批、超时和成本。
- `PlanStep`：步骤、依赖、能力、参数、状态、超时和审批要求。
- `ReactObservation`：工具、参数、状态、结果、事实摘要和错误。
- `ExecutionEvent`：供 SSE、消息详情和审计共同使用的版本化事件。

稳定状态只保存必要摘要和引用。超过 16KB 的 Observation 结果写入私有 Artifact Store，运行状态中保存 `data_ref`，避免模型上下文、数据库行和 SSE 载荷无限增长。

### 4.1.4 能力注册与动态召回

`CAPABILITY_REGISTRY` 是 Agent 权限和工具契约的事实来源。当前主要能力包括：

| 能力 | 副作用 | 是否审批 | 说明 |
|---|---|---|---|
| `job_query` | `none` | 否 | 查询本地岗位数据 |
| `resume_read` | `none` | 否 | 读取当前用户简历用于匹配分析 |
| `web_search` | `none` | 否 | 搜索公开网页 |
| `company_analysis` | `none` | 否 | 汇总公司公开信息 |
| `job_collect` | `local_persistent` | 是 | 采集并写入岗位 |
| `job_score` | `local_persistent` | 是 | AI 评分并更新数据 |
| `greeting_generate` | `local_persistent` | 是 | 生成并保存招呼语 |
| `greeting_send` | `external` | 是 | 向外部平台发送招呼语 |
| `reply_draft` | `local_reversible` | 是 | 生成 HR 回复草稿 |
| `reply_send` | `external` | 是 | 发送 HR 回复 |
| `reply_monitor` | `external` | 是 | 启动持续监测 |
| `pipeline` | `external` | 是 | 启动完整求职流水线 |

`CapabilityRetriever` 根据目标文本、标签、实体和用户约束召回少量相关能力。用户明确说“不要发送”时，发送类能力必须从可执行候选中剔除，而不是只依赖模型自觉遵守。

新增能力必须：

1. 在注册表声明明确的输入输出 Schema。
2. 独立标注风险等级与副作用类型。
3. 声明是否需要审批、超时和成本级别。
4. 通过统一执行入口，不向模型暴露任意 Python、SQL、浏览器或终端权限。
5. 增加能力召回、参数校验、策略拦截和失败行为测试。

### 4.1.5 ReAct 与 DAG 的选择

系统不会为所有问题强制生成完整计划：

- 单能力、短链路或探索式任务使用 ReAct，每轮根据最新 Observation 决定下一步。
- 多交付物、存在依赖或可并行的复杂只读任务使用 DAG。
- 有副作用的步骤不允许由只读 DAG 自主执行，必须转入审批。

`DagScheduler` 的安全约束包括：

- 执行前验证重复 ID、缺失依赖和循环依赖。
- 只调度全部前置步骤已完成的节点。
- 无依赖节点按批次并行，并受 `max_concurrency` 限制。
- 每个步骤有单独超时，整个 DAG 有总截止时间。
- 失败节点的后代标记为跳过，独立分支仍可保留有效结果。
- 每个并行批次前检查取消信号。
- 审批步骤只标记为 `awaiting_approval`，不交给自主执行器。

### 4.1.6 审批与副作用隔离

模型只能提出动作，不能为自己授权。产生副作用的请求生成包含动作 ID、参数、预览和影响对象的审批提案，通过 LangGraph interrupt 暂停。

审批恢复链路：

```text
Agent 生成提案 → RuntimeStore 持久化 → 前端显示审批卡片
→ 用户确认/修改/取消 → resume API → Command(resume=decision)
→ 再校验提案和业务状态 → 固定 action_dispatcher → 记录结果
```

执行时必须满足：

- 提案存在、未过期且尚未消费。
- 执行参数与用户最终批准参数一致。
- 当前岗位状态仍允许该动作。
- 发送器继续执行人工确认、时间窗口、日限和节流检查。
- 提案只消费一次；调度失败前不得错误消费，允许用户修正配置后重试。

进程内 `_consumed_actions` 只是快速保护，最终幂等事实由 Runtime Store 持久化。

### 4.1.7 会话、流式输出与取消

`AssistantService` 是 Web API 与 LangGraph 之间的边界：

1. 幂等创建会话并保存用户消息。
2. 为每轮请求创建唯一 Run。
3. 获取 `conversation:<id>` 会话锁，禁止同一会话并发运行两个 Agent。
4. 设置 Token、执行事件和取消检查回调。
5. 调用 `graph.ainvoke()`，以 `conversation_id` 作为 checkpoint `thread_id`。
6. 将 Token 和 `ExecutionEvent` 推送给 SSE 客户端。
7. 保存回答、引用、计划、工具轨迹、Observation 和运行摘要。

取消是协作式的：`POST /api/assistant/runs/{run_id}/cancel` 写入取消信号；DAG 在安全点停止后续节点。无法安全中断的外部 SDK 调用可能先完成，但取消后不得继续启动新步骤。被取消的部分回答由前端按 partial message 接口保存，不作为完整助手回答落库。

### 4.1.8 持久化与生产基础设施

问答 Agent 的可恢复运行依赖：

| 设施 | 事实边界 |
|---|---|
| PostgreSQL | 业务数据、会话、消息、LangGraph Checkpoint、Run、DAG 步骤、Observation、审批和制品引用 |
| Redis | 会话锁、取消信号和实时事件；不是最终事实来源 |
| Artifact Store | 超大工具结果、研究材料和生成文件 |
| Dramatiq | 仅运行显式注册的后台任务，禁止执行任意函数路径 |

当前 `build_assistant_graph()` 使用 `AsyncPostgresSaver`，问答 Agent 启动前必须配置可用的 PostgreSQL `database.url`。生产部署还应配置 Redis；组件不可用时应快速失败，不能静默退回导致多实例锁和取消失效的进程内模式。

### 4.1.9 可观测性与评测

执行事件统一覆盖理解、规划、检索、生成、审批、执行和收尾阶段。前端显示的计划进度、工具状态和错误信息都应来自同一份 `ExecutionEvent`，避免 UI 自行推测状态。

问答 Agent 的关键指标：

- 端到端任务完成率和成功标准覆盖率。
- 能力召回率、首次工具选择准确率、参数正确率。
- 平均无效工具调用次数和不必要追问率。
- DAG 并行批次、步骤失败率、超时率和取消响应时间。
- 用户否定约束遵守率与敏感动作拦截率。
- 无有效审批的外部执行次数，目标必须为 0。
- 过早结束、重复调用、重规划和预算耗尽比例。

反馈闭环由消息评分、Bad Case、执行轨迹和回归评测组成。修复问答问题时应优先增加完整场景测试，而不是继续堆叠意图关键词。

### 4.1.10 Agent 架构变更完成条件

问答 Agent 变更除通用 Definition of Done 外，还必须满足：

- 简单问答、单工具 ReAct、复杂只读 DAG、澄清和审批恢复各有回归测试。
- 用户说“不要发送/不要写入”时，相关能力在策略层被确定性阻止。
- DAG 循环、缺失依赖、超时、取消和部分失败均有测试。
- 同一会话并发请求被会话锁拒绝或排队，不产生交叉状态。
- Checkpoint 可按会话恢复，审批提案不可重复消费。
- SSE 事件、消息元数据和 Runtime Store 的状态相互一致。
- 大结果转存 Artifact Store，回答上下文保持有界。
- 所有外部动作仍经过原有固定执行器与业务安全检查。

### 4.1.11 证据域隔离改造基线

问答链路已增加确定性的证据域路由，当前使用以下模式：

| 模式 | 允许的只读能力 | 典型问题 |
|---|---|---|
| `direct` | 无 | “什么是岗位漏斗” |
| `structured_data` | `job_database` | “最近采集了多少岗位” |
| `private_document` | `resume_read` | “分析我的简历优势” |
| `public_current` | `web_search`、`company_research` | “某公司最近有什么新闻” |
| `mixed` | 由上述证据域组成 | “哪些岗位适合我，这些公司怎么样” |

实现约束：

- `respond()` 不再为普通问题无条件查询岗位数据库。
- 只有私有资料域才读取简历和相关长期记忆。
- 只有公开时效域且用户启用联网时才启动联网研究。
- 能力召回结果必须经过证据域工具白名单过滤。
- “什么是”“解释概念”等定义类问题默认直接回答，不能仅因包含“漏斗”“趋势”等词误触发问数。
- 问数、私有资料和联网结果逐步统一为 `EvidenceResult`，保留来源、时间、状态和缺失证据字段。
- 证据域路由只限制只读能力，不授予任何写入、发送或后台任务权限；副作用动作仍走既有审批链路。

### 4.1.12 统一证据与混合任务执行

第二、第三阶段改造在证据域隔离之上增加以下实现基线：

1. 问数、私有资料和联网研究统一返回 `EvidenceResult`，包含任务 ID、执行器、状态、证据、摘要、缺失项、有界数据和制品引用。
2. `EvidenceSynthesizer` 只消费标准证据，负责覆盖检查、引用去重和最终回答上下文；必需证据缺失时必须明确说明，禁止用模型常识补齐。
3. 超长数据在进入回答上下文前截断：结构化数据最多 50 行、简历最多 12000 字符、公开来源最多 12 条；更大的运行结果继续由 Artifact Store 保存。
4. 混合问题通过 `EvidenceTask` 建立固定依赖顺序：

```text
structured_data（查询候选岗位）
    → private_document（结合简历筛选，最多 5 个岗位/公司）
        → public_current（仅研究入围公司）
```

5. 现有 `DagScheduler` 继续负责依赖验证、并发上限、步骤超时、整体截止时间、取消和失败传播；具体执行逻辑下沉到 `assistant/executors/`。
6. 专业执行器边界：

| 执行器 | 输入 | 输出 | 禁止行为 |
|---|---|---|---|
| `analytics` | 结构化问题 | 受限查询结果 | 不得失败后自动联网 |
| `private_docs` | 简历与前序候选 | 匹配摘要、入围岗位和公司 | 不得联网或修改资料 |
| `web_research` | 用户问题与入围公司 | 有界公开来源 | 不得扩散研究全部候选 |

7. 会话消息元数据同时持久化 `evidence_route`、`evidence_tasks`、`evidence_results` 和 `evidence_coverage`，便于前端展示、Bad Case 复盘和离线评测。

## 5. 数据模型与状态机

业务数据、Agent 运行状态和检查点统一保存在 `database.url` 指向的 PostgreSQL 数据库中，不提供 SQLite 运行时降级。主要实体包括：

- `jobs`：岗位详情、评分、招呼语、会话和当前状态。
- `history`：发送、回复、简历等业务历史。
- `job_events`：岗位状态变更事件。
- `risk_events`：限流或风险事件。
- `workbench_tasks`：Web 后台任务状态、日志和停止原因。

主要状态流：

```text
pending
  ├── filtered
  └── scored → ready → approved → sent
                │         │         ├── replied → needs_resume → resume_sent
                │         │         └── follow_up_sent
                │         └── error ──有限退避重试──→ approved
                └── rejected
```

实现新状态时必须同时检查：

- 数据查询和漏斗统计口径。
- CLI `status`、Web 列表和前端状态标签。
- 合法状态迁移及事件记录。
- 失败重试是否可能造成重复发送。
- PostgreSQL Schema 迁移与测试数据兼容性。

不得通过直接修改数据库状态来跳过人工确认。

## 6. 配置设计

配置来源以项目根目录 `config.yaml` 为主，示例定义在 `config.example.yaml`，Web 校验定义在 `src/bosshunter/web/config_schema.json`。

主要配置域：

| 配置段 | 责任 |
|---|---|
| `profile` | 简历、头像、目标岗位、城市、薪资和排除条件 |
| `search` | 关键词、城市、页数和排序 |
| `scoring` | 阈值、候选上限、并发和硬过滤 |
| `throttle` | 日限、间隔、时间窗、浏览、错误退避 |
| `ai` | 提供商、模型、凭据、超时、重试和生成质量 |
| `resume` | 模板、主题、头像和 ATS 版本 |
| `monitor` / `follow_up` | 回复监测和跟进策略 |
| `browser` | CDP Proxy、端口、浏览器和用户目录 |
| `database` / `runtime` / `artifacts` | 生产基础设施后端 |

新增配置字段的完成条件：

1. 为旧配置提供默认值，不破坏现有安装。
2. 更新 `config.example.yaml` 和 Web Schema。
3. Web API 读写保持类型一致并对敏感值脱敏。
4. 添加配置加载、保存或接口测试。
5. 更新操作手册中用户可见的行为。

## 7. Web API 与后台任务

`web/server.py` 暴露健康检查、漏斗、岗位、历史、工作台、配置、简历、头像和助手相关 API。静态前端由同一 Bottle 应用提供。

安全规则：

- `/api/*` 数据和操作接口应经过本地访问保护。
- 配置读取和下载复用同一套脱敏逻辑。
- 文件上传必须限制类型、大小和落盘路径。
- 下载接口只能访问预期的制品目录，防止路径穿越。
- 错误响应不得回显凭据、简历全文或内部堆栈。

`WorkbenchTaskRunner` 管理后台任务：

- 运行任务使用停止事件协作退出。
- 高风险工作台任务原则上互斥；仅显式声明为安全的模式可并行。
- 到达发送时间窗口截止点时自动请求停止。
- 服务重启后，遗留运行中任务标记为停止，不自动恢复。
- 任务线程必须有明确终态：`completed`、`failed` 或 `stopped`。

新增后台动作不得自行创建无限线程、脱离任务记录或绕过互斥锁。

## 8. AI 提供商与生成链路

AI 提供商分发集中在 `ai/credentials.py`：

- `anthropic`：Anthropic Messages 或兼容接口。
- `openai_compatible`：OpenAI 兼容 Chat Completions 接口。
- 兼容服务可设置 `base_url`，模型发现和模糊匹配不得写死服务名称。

开发要求：

- Mock AI 边界，测试不得依赖真实网络和额度。
- 区分可重试的 429、5xx、网络错误与不可重试的配置错误。
- 限制并发、超时和最大重试次数。
- 日志不得包含 API Key、完整请求头或不必要的简历正文。
- 生成内容是建议，不得替代人工事实校验。

## 9. 浏览器自动化与选择器维护

浏览器连接流程：

```text
发现 Chrome/Edge → 启动或连接调试端口 → 启动 CDP Proxy
→ RuntimeClient 健康检查 → 定位平台页面 → 执行业务动作
```

选择器是高变动边界。修复流程：

1. 在测试账号和低风险场景复现问题。
2. 保存最小必要的 DOM 特征，禁止提交个人聊天内容。
3. 优先更新 `scraper/`、`executor/` 或 site pattern，不扩散选择器常量。
4. 对旧、新结构增加确定性测试。
5. 验证找不到元素时安全失败，不误点相邻按钮。
6. 发送类变更必须人工进行小规模烟雾测试。

禁止添加规避风控、验证码或平台安全检测的实现。

## 11. 测试策略

测试文件位于 `tests/test_*.py`。修改后至少执行受影响测试，提交前执行完整测试。

| 变更类型 | 必测内容 |
|---|---|
| CLI / 配置 | 参数、默认值、旧配置兼容、脱敏 |
| 数据层 | 状态迁移、统计口径、重复执行、升级 |
| 选择器 | 新旧页面结构、缺失元素、安全失败 |
| 发送 | 未批准不发送、时间窗、日限、重试不重复 |
| 监测 | 回复分类、简历请求、建议内容不自动发送 |
| Web API | 状态码、输入校验、并发冲突、停止行为 |
| 前端 | `npm run build`、关键交互和状态映射 |
| PDF | 模板渲染、事实保真、页数和 ATS 输出 |

真实浏览器、网络和 AI 调用应在单元测试中 Mock。需要人工烟雾测试时，使用最小数据集并记录验证步骤。

## 12. 变更流程

### 12.1 需求准入

任何新需求在开发前回答：

1. 是否直接改善“采集、筛选、确认、沟通、监测”闭环？
2. 是否有真实用户问题或可复现缺陷，而非仅仅“可能有用”？
3. 能否通过配置、文档或已有能力解决？
4. 是否扩大账号、隐私、法律或维护风险？
5. 是否有明确验收标准、测试方式和后续维护人？

以下任一情况默认不进入开发：

- 绕过人工确认、平台安全控制或验证码。
- 仅为提高投递数量而提高默认频率或并发。
- 与个人求职闭环无关的通用平台能力。
- 无法写出验收标准或无法稳定测试的功能。
- 引入长期基础设施成本但没有明确使用场景。
- 与现有能力重复，仅增加新的入口或抽象层。

### 12.2 小步实现

1. 先建立 Issue，描述问题、范围外内容、风险和验收标准。
2. Bug 先增加失败测试；重构先锁定现有行为。
3. 将改动拆成可独立验证的小步骤。
4. 只修改任务相关文件，保留用户已有工作区改动。
5. 完成代码、测试、文档和发布制品后再结束任务。

### 12.3 完成定义（Definition of Done）

一个变更只有同时满足以下条件才算完成：

- 验收标准全部通过，范围外需求未被顺带加入。
- 相关测试和完整测试通过，Ruff 检查通过。
- 前端变更通过 `npm run build` 且 `dist/` 已同步。
- 没有削弱人工确认、节流、隐私和任务互斥。
- 新配置、命令或行为已更新文档。
- 日志和接口响应不泄露敏感数据。
- `git diff` 已审查，无无关文件、运行数据或密钥。

## 13. 控制“无限开发”的治理规则

项目按稳定产品维护，不按功能数量衡量进度。

### 13.1 版本冻结条件

满足以下条件时进入功能冻结，仅接受严重 Bug、安全修复、选择器适配和文档更新：

- 核心闭环可从 CLI 和 Web 各完成一次。
- 关键安全测试覆盖人工确认、日限、时间窗和重复发送。
- 安装、首次配置、停止和恢复流程有文档且可复现。
- 已知 P0/P1 缺陷清零，P2 缺陷有明确处置。
- 发布检查可以重复执行并得到稳定结果。

### 13.2 维护优先级

```text
安全/隐私问题 > 数据损坏或重复发送 > 核心流程不可用
> 平台选择器适配 > 可观测性和文档 > 体验优化 > 新功能
```

### 13.3 WIP 限制

- 同一时间只推进一个产品功能。
- 没有完成测试和文档的功能不得开启下一个功能。
- 新想法进入 Issue/Backlog，不直接进入代码。
- 连续两个版本使用率低、维护成本高的实验功能应评估删除或冻结。

### 13.4 停止开发判定

出现以下情况应停止当前开发并重新评审：

- 需求开始改变产品定位或绕过安全边界。
- 为修复一个问题引入多个新服务或长期运维负担。
- 反复调整实现但验收标准没有变化或仍不明确。
- 测试无法稳定复现，真实效果只能依靠主观判断。
- 变更收益小于账号、隐私、兼容性或维护风险。

## 15. 运维与故障等级

| 等级 | 示例 | 处理 |
|---|---|---|
| P0 | 泄露密钥/简历、绕过确认、重复批量发送 | 立即停止服务，隔离数据，撤销凭据，优先修复 |
| P1 | 核心流程不可用、数据库损坏、错误状态导致误发送风险 | 停止相关功能，保留证据，回归测试后发布修复 |
| P2 | 单个选择器失效、部分 AI 提供商异常、PDF 模板问题 | 降级或人工操作，排期修复 |
| P3 | 文案、样式、小型体验问题 | 进入 Backlog，随维护版本处理 |

故障期间不要删除数据库或浏览器配置。先停止任务、备份相关文件、记录版本与最小复现步骤，再进行只读诊断。
