# BossHunter 前端设计系统 与 shadcn 接入方案

> 状态：**待批准**（本文只是方案，尚未改动任何项目文件）
> 适用版本：BossHunter 2.0 前端（`src/bosshunter/web/frontend/`）
> 前置约束：调色板数值与 Inter 字体**不变**（上一轮明确冻结）；已有 9 个手写 `components/ui/*` **保留**

---

## 1. 结论

走**不动框架**的接法：

| 决策 | 取值 |
|---|---|
| 组件库 style | **`new-york`**（v3 时代风格） |
| Tailwind | 保持 **v3.4**，继续用 `tailwind.config.ts` |
| React / Vite / TS | 保持 18.3 / 6.4 / 5.4，**不升级** |
| 调色板 | 数值不变。新增 14 个 Tailwind 颜色键，**全部别名到既有 CSS 变量** |
| 字体 | 保持 Inter，不引入 Geist |
| 现有组件 | 保留 `button / card / input / textarea / select / badge / slider / switch / tags-input` |
| 新增组件 | `dialog`、`form`、`table`（另带 `label`） |
| 需要改动的既有代码 | **8 处 class 名**（`text-muted` → `text-muted-foreground`） |
| 新增依赖 | 4 个（见 §5） |

**为什么不用官方 `init`**：实测它生成的是 Tailwind v4 + React 19 + Vite 8 + TS 6 + `radix-nova` preset + Geist 字体。那会重写 `globals.css`、删掉 `tailwind.config.ts`、替换 teal 调色板与 Inter，并需要重验 recharts / react-hook-form 兼容性、重建入库的 `dist/`。这与冻结约束冲突，且是本次改动量的 10 倍以上。

## 2. 依据（全部实测，非推断）

### 2.1 `init -t vite` 是"新建项目"
在空目录执行会询问 *"Would you like to set up a monorepo?"*；加 `--no-monorepo --name bh-ref` 后它**创建了子目录 `bh-ref/`** 并在其中盖了新项目。现有项目应使用不带 `-t` 的 `init`。

### 2.2 `radix-nova`（v4）在 Tailwind v3 上不可用
从注册表实际拉取 `https://ui.shadcn.com/r/styles/radix-nova/*.json` 后比对：

| 事实 | 影响 |
|---|---|
| 组件使用 `outline-hidden` | **v4 专有工具类**，v3 不生成 |
| `form.json` 的 `files` 为 **空数组** | radix-nova **没有 form 组件** |
| 组件 `npm deps: ["cn"]` | 依赖新的 `cn` 包，而非项目的 `@/lib/utils` |
| 用到 `--radius-md`、`bg-input`、`border-ring`、`ring-foreground` | v4 时代的变量约定 |
| `button` 用 `bg-clip-padding` + `--secondary` 变量 | 与 v3 语义层不一致 |

### 2.3 `new-york`（v3）与项目兼容
| 项 | 实测值 |
|---|---|
| `files` 路径 | `ui/dialog.tsx`、`ui/form.tsx`、`ui/table.tsx` … |
| npm deps | `@radix-ui/react-dialog`、`@radix-ui/react-label`、`@radix-ui/react-slot`、`@hookform/resolvers`、`react-hook-form`、`zod`（后三者**项目已有**） |
| `form` 的 registryDependencies | `["button", "label"]` ← 注意会带上 button |
| 动画类 | `slide-in-from-top-2` 等 → 需要 `tailwindcss-animate` |
| `cn` 导入 | `@/lib/utils` ← 项目已有，**兼容** |

### 2.4 三个命令的实际结果
| 你的命令 | 结果 |
|---|---|
| `npx shadcn@latest init -t vite` | ❌ 会新建项目；且交互式（先问组件库 Base UI/React Aria/Radix UI，再问 preset Nova/Vega/Maia…），`--yes` 跳不过 |
| `npx shadcn@latest add button card dialog form table` | ⏸ 未执行（依赖 init 与 style 决策） |
| `npx skills add shadcn/ui` | ❌ **失败**：`git clone https://github.com/shadcn/ui.git` → `Recv failure: Connection was reset`。放宽超时到 600s 后暴露真实原因是 **github.com 连接被重置**，不是超时，调超时无用。注册表（npm / ui.shadcn.com）可达，GitHub 不可达 |

### 2.5 改动面实测
| 指标 | 数量 |
|---|---|
| `text-muted` 调用点 | **8**（唯一的语义冲突，见 §4） |
| `bg-muted` 调用点 | 0 |
| `window.confirm()` 调用点 | **9**（分布在 `AIAssistantPage.tsx`、`DashboardPage.tsx`） |
| 原生 `<table>` | 2 个文件（`JobsTable.tsx`、`ui/table.tsx`）——**见 §13 更正** |

## 3. Token 映射表

原则：**不新增任何颜色数值**。shadcn 的语义名全部指向项目已有的 CSS 变量。

### 3.1 无需新增（名字已存在且语义一致）

| shadcn token | 项目现有映射 | 现有值 |
|---|---|---|
| `background` | `--color-background` | `246 247 249` |
| `foreground` | `--color-foreground` | `15 23 42` |
| `primary` | `--color-primary` | `15 118 110`（teal） |

### 3.2 需要新增的颜色键（全部别名到既有变量）

| 新增 Tailwind 键 | 指向的既有变量 | 解析值 | 用途 |
|---|---|---|---|
| `card` | `--color-surface` | `255 255 255` | 卡片底 |
| `card-foreground` | `--color-foreground` | `15 23 42` | 卡片文字 |
| `popover` | `--color-surface-overlay` | `255 255 255` | 弹层底 |
| `popover-foreground` | `--color-foreground` | `15 23 42` | 弹层文字 |
| `primary-foreground` | 常量 | `255 255 255` | 主按钮文字 |
| `secondary` | `--color-surface-raised` | `252 252 253` | 次级表面 |
| `secondary-foreground` | `--color-foreground` | `15 23 42` | 次级文字 |
| `muted` | `--color-surface-raised` | `252 252 253` | 弱化**表面**（见 §4） |
| `muted-foreground` | `--color-text-tertiary` | `100 116 139` | 弱化**文字** |
| `accent` | `--color-background` | `246 247 249` | hover 填充（白底上可见且克制） |
| `accent-foreground` | `--color-foreground` | `15 23 42` | hover 文字 |
| `destructive` | `--color-danger` | `220 38 38` | 危险动作 |
| `destructive-foreground` | 常量 | `255 255 255` | 危险动作文字 |
| `border` | `--color-card-border` | `228 232 239` | 描边 |
| `input` | `--color-card-border` | `228 232 239` | 输入框描边 |
| `ring` | `--color-primary` | `15 118 110` | 焦点环（teal） |

`--border: #E4E8EF` 与 `--color-card-border: 228 232 239` 是**同一个颜色**，因此新增 `border` 键不会改变现有任何描边的渲染。

### 3.3 优先级更高的做法（建议采纳）
新增的颜色键直接**引用既有变量**而不是重复字面量：

```ts
// tailwind.config.ts — colors 段追加（既有键一律不动）
card: { DEFAULT: 'rgb(var(--color-surface) / <alpha-value>)', foreground: 'rgb(var(--color-foreground) / <alpha-value>)' },
popover: { DEFAULT: 'rgb(var(--color-surface-overlay) / <alpha-value>)', foreground: 'rgb(var(--color-foreground) / <alpha-value>)' },
'primary-foreground': 'rgb(255 255 255 / <alpha-value>)',
secondary: { DEFAULT: 'rgb(var(--color-surface-raised) / <alpha-value>)', foreground: 'rgb(var(--color-foreground) / <alpha-value>)' },
muted: { DEFAULT: 'rgb(var(--color-surface-raised) / <alpha-value>)', foreground: 'rgb(var(--color-text-tertiary) / <alpha-value>)' },
accent: { DEFAULT: 'rgb(var(--color-background) / <alpha-value>)', foreground: 'rgb(var(--color-foreground) / <alpha-value>)' },
destructive: { DEFAULT: 'rgb(var(--color-danger) / <alpha-value>)', foreground: 'rgb(255 255 255 / <alpha-value>)' },
border: 'rgb(var(--color-card-border) / <alpha-value>)',
input: 'rgb(var(--color-card-border) / <alpha-value>)',
ring: 'rgb(var(--color-primary) / <alpha-value>)',
```

这样暗色主题只需改 `globals.css` 里既有的 `--color-*` 值，**新组件自动跟随**，不需要为暗色维护第二套 token。

## 4. 唯一的语义冲突：`muted`

shadcn 里 `muted` 是**表面**（`bg-muted`，用于表头、滚动区），`muted-foreground` 是**文字**。
项目里 `muted` 是**文字色**（`--color-muted: 100 116 139`，用在 8 处 `text-muted`）。

**如果不处理**：`table` 的表头会变成 `#64748B` 的深灰底，`select` 的滚动按钮同理 —— 明显的视觉错误。更糟的是这会变成**长期陷阱**：以后 AI 每加一个 shadcn 组件都会踩一次。

**处理方式**（唯一需要碰既有代码的地方）：

1. `muted` 改为弱化表面 = `--color-surface-raised`
2. `muted-foreground` = `--color-text-tertiary`（`#64748B`，与现在的 `text-muted` 渲染**完全一致**）
3. 机械替换 **8 处** `text-muted` → `text-muted-foreground`

替换后**像素级无变化**，但词汇表与 shadcn 标准对齐 —— 这正是"让 AI 首次就生成对"的前提。

`accent-*` 与 `border-border` 现有用法为 0，可安全新增。

## 8. 设计决策（"设计 UI"的实质部分）

以下 9 条是本轮真正要落地的设计改动，按优先级排列。它们同时消化了上一轮批判里**已确认但未修**的遗留项。

### 8.1 字号系统（P1）——**实施方式已变更，见 §13.1**
现状实测：`9px / 10px / 11px / 12px / 13.12px / 15px / 16px / 18px / 20px / 24px` 混用，其中 `text-[10px]` 在展开的执行记录里占 **10/14 个文本节点**。

~~目标固定 rem 级差：把 `text-xs` 重定义为 11px、`text-sm` 重定义为 13px。~~
**实际做法**：项目现有的 Tailwind 阶梯（12/14/16/18/20/24，比值 1.11–1.20）本身已经合规，
真正的问题只是 **58 处 `text-[Npx]` 硬编码覆盖**。因此做法是删掉这些覆盖、回到既有阶梯，
而不是重定义 `text-xs`/`text-sm`（那会波及数百处既有用法，收益相同、风险大得多）。

### 8.2 状态词汇统一为一套（P1）
现在有**三套**状态配色并存（`eventStatusClass`、`businessStageStatusClass`、以及 JSX 里手写的 chip）。统一为一个 `<StatusChip status tone>` 原语，tone 取自既有语义色，并把「跳过/未收到终态/已取消」的**文字标注**收进去（不能只靠颜色）。同时把 `ui/badge.tsx` 真正用起来。

### 8.3 执行记录移到答案之后（上一轮遗留的 P1-a）
上一轮你选了"压成一行、答案优先"，我只做了折叠 + 一行诚实摘要，**位置没动**。本轮建议补上：`ExecutionRecord` 移到答案与来源之间，让阅读顺序变成「问题 → 答案 → 证据 → 过程」。

### 8.4 对比度 4.44:1（P2，现在有正当解）
展开态执行记录 **14 个文本节点里 9 个是 4.44:1**，差 0.06 不达 AA。根因是 `--color-text-tertiary` 的数值——但你冻结了调色板数值。
**解法**：不动 token，把该处的 class 从 `text-text-tertiary` 换成 `text-text-secondary`（`71 85 105`，实测 10.35:1）。零调色板改动，达标。

### 8.5 Dialog 替掉 9 处 `window.confirm`（P1）
原生 confirm 的已知问题：阻塞式、无法样式化、无法显示"将要发生什么"、移动端体验差、且**破坏产品的确认语义**（本项目核心承诺就是人工确认要清楚）。
用 `dialog` + `alert-dialog` 语义重做，每处写清"将发生 / 不会发生"，并加 Esc / 焦点陷阱 / 键盘可达。

### 8.6 Table 用于岗位池（P2）——**已撤销，前提不成立**
`JobsTable.tsx:93-116` 本来就用了原生 `<table>/<thead>/<tbody>/<th>/<td>`，语义与键盘导航均已具备。
原先"0 个原生表格"是误测（PowerShell `**` glob 未递归进 `components/dashboard/`）。
**结论：不做改造**——纯样式 churn 会引入回归风险而无实质收益。

### 8.7 动效规范（P2）
统一 150–250ms、`ease-out` 指数曲线；**每个动画都要有 `prefers-reduced-motion: reduce` 替代**（项目已有部分，需补齐）；不加编排式入场动画（product register 明确反对）。

### 8.8 焦点与可达性收口（P2）——**原测量是启发式假象，见 §13.3**
~~实测 89 个交互元素中 35 个无任何焦点样式。~~
用「Tab 遍历 + 对比聚焦前后计算样式」的真实键盘测量取代了 class 字符串匹配：
**五条路由 `no-indicator` 均为 0**，即不存在 WCAG 2.4.7 失败；真正的问题是约 **183 个元素只依赖浏览器默认 outline**。
修法：在 `globals.css` 加一条 `:where(...):focus-visible` 兜底（用 `:where()` 压到 0 特异度，组件自身样式仍可覆盖）。

### 8.9 `aria-live` 每秒播报（P2）
执行记录容器挂了 `aria-live="polite"` 且内含每秒刷新的耗时文本。运行中会让屏幕阅读器每秒播报一次，用户无法听答案。改为只在**阶段状态变化**时更新 live region。

## 13. 实施记录与测量更正

本文 §2 与 §8 里有三处测量在实施过程中被**证伪**，原因都是测量方法本身有缺陷。保留此节以便后续不再重复同样的错。

### 13.1 §8.1 的实施方式变了（不是重定义阶梯）
- 原方案：重定义 `text-xs` = 11px、`text-sm` = 13px。
- 实测：项目现有 Tailwind 阶梯（12/14/16/18/20/24）比值 1.11–1.20，**本身已合规**。
  真正的问题是 **58 处 `text-[Npx]` 硬编码**（`text-[9px]`×1、`text-[10px]`×24、`text-[11px]`×30、`text-[15px]`×1，分布在 11 个文件）。
- 实际做法：把这 58 处归回既有阶梯（`text-xs` / `text-base`），**不动 `tailwind.config.ts` 的字号**。
  这样达到同样的词汇统一目标，但不波及数百处既有 `text-xs`/`text-sm` 用法。
- 验证：递归扫描 `text-[Npx]` 归零；五条路由全部 `pageHorizontalOverflow=false`；
  残留的"clipped"计数全部是既有的 `truncate`/`max-w-*` 有意截断；字体阶梯实测收敛为
  12/14/16/20/24（`/assistant` 另有 15px 正文、13.12px 表格、0.86em 代码、10px 引用角标——
  这些来自 `globals.css` 的 markdown 排版层，是有意的正文排版，不属于工具类混乱）。

### 13.2 §2.5「原生 `<table>` = 0」是误测
`JobsTable.tsx:93-116` 一直在用原生 `<table>`。原因是统计时用的 PowerShell
`Select-String -Path "src\**\*.tsx"` **不会递归进子目录**，漏掉了 `components/dashboard/`。
后续统计一律改用能真正递归的检索方式。

### 13.3 §8.8「35 个元素无焦点样式」是启发式假象
- 原方法：检查 `className` 里有没有 `focus-visible:`/`ring` 之类字符串。
  这会漏掉两类情况：焦点样式来自**祖先的 `focus-within`**（例如 `tags-input` 容器），
  或来自**浏览器默认 outline**。
- 真实方法：用 CDP 发送 `Tab` 键遍历，逐元素对比聚焦前后的
  `outline / box-shadow / border-color / background-color`，并向上比 5 层祖先。
- 真实结果：**五条路由 `no-indicator` 全为 0**（不存在 WCAG 2.4.7 失败）；
  约 183 个元素只用浏览器默认 outline（侧栏导航、模式卡、筛选 chip、折叠标题）。
- 修法：`globals.css` 增加
  `:where(a, button, input, select, textarea, summary, [tabindex]):focus-visible { outline: 2px solid rgb(var(--color-primary) / 0.55); outline-offset: 2px; }`
  用 `:where()` 把特异度压到 0，因此 `.outline-none`（utilities 层，顺序在后）与
  `focus-visible:ring-*`（特异度更高）仍可覆盖它——实测 `<Button>` 保持自己的 box-shadow ring。
