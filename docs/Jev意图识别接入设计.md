# Jev 意图识别接入设计

日期：2026-10-09。分支：`feat/jev-intent-design`。本文仅定义设计，不改变当前执行行为。

## 目标与实测依据

使用 Jev 识别有限业务意图和交互模式，减少理解层对自由文本 JSON 的依赖；保留现有实体提取、规划、长期记忆与人工确认能力。

已通过 Windows PowerShell 验证：`GET /v1/models` 与 `POST /v1/systemone` 均返回 HTTP 200。`jev-latest` 实际返回 `jev-1.13.0`。输入“帮我找深圳的 Python 岗位，先不要发送招呼语。”时，四候选分类返回 `job_search`，分类 confidence 为 1.0，禁止发送 Noul 值为 0.95。这是单条连通性测试，不代表十二类意图、多轮中文准确率或线上延迟保证。

此前 WSL 请求返回 HTTP 451，PowerShell 成功。只能确认执行环境网络路径存在差异，尚未证明具体代理原因。实际应用进程及 Docker 容器也须单独验证；PowerShell 成功不能代替部署环境验证。451 直接报告地区不可用，不通过反复重试或更换模型解决。

## 方案选择

| 方案 | 收益 | 代价 | 决策 |
| --- | --- | --- | --- |
| Jev 独立分类，LLM 处理开放字段 | 边界清晰，沿用现有行为，可逐步增加快速路径 | 复杂请求可能多一次网络往返 | 推荐 |
| Jev 仅影子评估 | 不改变路由，能积累对照数据 | 初期增加成本，没有速度收益 | 推荐作为第一阶段 |
| Jev 完整替换任务理解 | 理想情况下少一次生成模型调用 | 不能直接生成任意公司名、目标、步骤及记忆内容 | 不采用 |

## 现有链路与接入位置

`graph.py` 调用 `understanding.extract_goal()`，随后构建目标状态并由 `routing.decide_route()` 分流。理解函数不只分类，还提取 entities、constraints、steps、memory_operations，归一化、纠正特例、调用 `apply_intent_policy()` 并延续待补全意图。能力注册表是实体契约来源。

拟新增模块：

- `ai/jev.py`：专用 HTTP 客户端、超时、错误分类及响应校验，不依赖聊天补全协议。
- `assistant/intent_classifier.py`：构建最小输入，定义问题和候选描述，将响应转换为独立分类证据。
- `assistant/understanding.py`：编排模式选择及最终 IntentResult 组装，保留统一后处理链路。
- `assistant/models.py`：新增分类证据契约，保留当前 IntentResult 接口。

复用已有 HTTP 依赖与配置习惯；开发前确定当前图节点调用的同步/异步边界，不在异步线程中直接阻塞事件循环，不新增无限制后台线程。

## 输入与问题定义

输入复用 `ContextSnapshot` 的已裁剪上下文：当前用户消息、近期必要对话、待补全意图摘要、选中岗位标识、有效待确认任务的最小摘要。不要直接发送完整数据库、工具轨迹、简历或长期记忆全集。明确区分用户原话、助手内容和数据来源，历史内容不能成为系统授权。

单次请求并行评估以下问题：

| 问题 | 类型 | 输出用途 |
| --- | --- | --- |
| 主要业务意图 | Choice | 当前十二种 IntentType 加 `unknown`；无法映射时回退 |
| 当前交互模式 | Choice | answer / execute / draft / confirm / cancel / unknown |
| 当前发言与待办的关系 | Choice | new_request / supplement / correction / confirmation / cancellation / unknown |
| 是否明确限制发送 | Noul | 作为约束补充信号，只能收紧权限 |
| 是否要求多个业务动作 | Noul | 决定是否需要原有理解和规划能力，不能生成步骤 |

候选描述区分本地岗位查询和新增搜索、普通寒暄和 HR 招呼语、公司单点事实和综合背调、起草和实际发送。枚举从本地契约构造，描述有版本号；程序对问题 ID、枚举、数值范围、有限数值及必需字段做校验。

`choice` 请求使用 `instructions` 和 `criteria`；二元判断使用 `type=noul`，不使用 `type=boolean`。概率和 confidence 分别保存，Noul 值不能冒充 Choice confidence。

## 分类证据与路由决策

分类证据包含：模型实际版本、问题配置版本、主意图及概率分布、主意图 confidence、模式分布及 confidence、待办关系、禁止发送概率、多动作概率、耗时和错误类别。问题之间独立评估，不假设结果必然一致。

Jev 证据在适配器内完成联合判定，不直接覆盖 `IntentResult.confidence`。现有 0.6/0.85 路由阈值适用于原理解输出，不能直接照搬为 Jev 的放行条件。第一阶段只收集分数；第二阶段通过独立验证集确定每类门槛，同时考察最大概率、confidence、前两候选差距和问题间冲突。阈值与适配策略均需版本化。

混合模式下：

1. 普通寒暄继续走现有确定性路径。
2. 调用 Jev；unknown、低分、关系歧义、模式与动作冲突、复杂请求或开放字段无法可靠补全时，调用原有 LLM 理解。
3. 简单请求只有在分类通过验证门槛、能力契约字段齐全、没有待办关系歧义且其他理解职责得到保留时，才可跳过 LLM。
4. 实体仅来自用户明确文本、可信选中岗位和已存在的待补全实体。任意城市、关键词、公司名无法可靠提取时调用 LLM；不让 Choice 在没有候选依据时猜测实体。
5. 一律经过现有归一化、公司/寒暄纠正、策略约束、待补全衔接及实体契约检查，然后才进入既有路由和规划。

复杂场景的 Jev 证据可作为 LLM 的分类建议输入，但不作为系统指令；LLM 分歧进入记录和保守处理，不能简单挑选更高分的结果。禁止发送信号保守合并，任何冲突不能撤销显式禁令。

## 安全、记忆与确认

- 风险等级和副作用由能力注册表、策略代码决定，模型不能降低风险。
- 分类成功只能决定走哪个处理流程，不能绕过人工确认、发送窗口、频率或有效授权检查。
- “可以”“好的”只有关联到当前有效待确认任务时才是确认候选。最终审批继续复用现有确认机制；无有效待办时不构造授权。
- 取消必须关联明确任务；无法区分“取消上一条发送”与“停止采集”时澄清。
- 原理解层自动提取 memory_operations。默认自动记忆模式下，第一版混合接入仍保留 LLM 理解，不能为了快速路径静默丢失记忆。只有原配置不要求自动提取，或以后有独立且经过批准的记忆方案，才启用对应快速路径。
- 配置关闭 Jev 时回到原有流程，既有模型异常降级行为保持原样；新增组件不得扩大规则降级的执行权限。

## 配置与故障处理

建议配置位于 `assistant.intent_classifier`：`mode=llm|shadow|hybrid`（默认 llm）、`provider=typesafe`、`model=jev-latest`、API 地址、密钥环境变量名、总超时和策略版本。密钥使用 `TYPESAFE_API_KEY` 等环境变量注入，配置示例和日志不包含实际密钥；配置 API 仅显示是否已配置。不要更改主回答模型的 provider 来接入 Jev。

设计目标是将影子评估总等待控制在约 3 秒；第一版先采用各网络阶段 3 秒的超时，不提供严格总截止保证，默认不重试。后续严格总预算实现后，才考虑预算内的网络短暂故障、429 或 5xx 有限重试。401/403 为鉴权或权限问题，451 为地区不可用，422 为请求契约问题，均不自动重试。解析失败、缺少答案、非法概率、模型不可用及超时回退原有 LLM；取消信号优先，不因取消转而启动备用请求。

错误日志仅记录路径、状态、错误类别、耗时和请求关联标识。默认不保存用户原文，影子样本需脱敏或使用合成数据。生产环境应固定评测通过的具体模型版本；使用 latest 时记录实际版本，模型更新后重新评估。

## 验证和逐步上线

第一阶段：客户端及影子模式。现有输出和执行行为不变；对相同上下文取得 Jev 分类证据。Jev 与旧 LLM 的一致率仅作分析，人工标签才是准确率基准。影子失败不能阻断原流程，调用需有时间预算。

第二阶段：构建人工标注中文评测集，覆盖十二类、交互模式、否定、歧义、多轮指代、多动作、未知请求和任务确认。建议每类至少 20 个样本，额外增加安全边界样本；按会话拆分调试集和验证集，避免相近改写泄漏。门槛选择使用验证集，最终验收另保留测试集。

重点样本：

| 输入与上下文 | 预期行为 |
| --- | --- |
| 你好 | 普通问答，不生成岗位招呼语 |
| 哪些岗位没有评分 | 本地查询，不启动评分 |
| 帮我找深圳的 Python 岗位，先不要发送招呼语 | 搜索，禁止发送 |
| 怎么回复 HR 比较好 | 起草或建议，不能发送 |
| 腾讯旗下有哪些业务 | 普通事实问答，不启动全面背调 |
| 查一下腾讯公司的情况 | 公司研究，提取公司名 |
| 换成深圳（正在补全搜索城市） | 延续原搜索目标，修改城市 |
| 可以（没有待确认任务） | 不作为发送授权 |
| 可以（有有效待确认任务） | 确认候选，交给既有审批机制 |
| 找岗位、评分，只生成招呼语 | 保留多步骤及禁发约束，走 LLM/Planner |

第三阶段：按意图逐类开启混合模式，先验证只读和无外部副作用场景；高风险发送分类仍经过现有人工确认。达到稳定效果后才扩大快速路径，不承诺所有请求都少一次 LLM 调用。

验收指标：macro-F1、各类召回、未知输入拒判、模式/待办关系准确率、禁止发送约束保留率、误进入副作用流程次数、回退率、端到端 P50/P95 延迟、每请求 token/成本。安全用例中绕过确认和撤销显式禁令必须为零；任何误判都需修复并补充回归样本，不能用整体准确率掩盖。

自动化测试 mock HTTP、LLM 和执行器，覆盖 200/401/403/422/429/451/5xx、超时、坏响应、分数边界、分歧合并、自动记忆保留、待补全及审批流程。禁止在测试中真实发送招聘消息。实现完成后运行相关 pytest、ruff，并在实际部署环境以合成文本做一次接口烟测；开放 PR 前按仓库要求运行全套测试。

## 待决策事项

第一版推荐仅实现客户端与影子模式，保留全部现有理解职责；完成评测后再单独批准启用混合快速路径。当前不需要调整工作台界面、不训练分类器，也不修改岗位评分、招呼语生成和发送模块。

## 第一阶段使用方式

已实现客户端和 `shadow` 模式，默认仍为 `llm`。在本地配置的 `assistant` 节点中添加：

```yaml
assistant:
  intent_classifier:
    mode: shadow
    provider: typesafe
    model: jev-latest
    api_key_env: TYPESAFE_API_KEY
    timeout_seconds: 3
```

在启动应用的 PowerShell 进程中设置 `$env:TYPESAFE_API_KEY = '<你的密钥>'`，再启动应用。密钥不写入配置或仓库。与真实调用一样，应用进程需要能访问 TypeSafe；开发客户端使用 httpx，PowerShell 的系统代理不会自动保证 Python 也使用相同出口。如需显式代理，为该应用进程按实际代理地址设置 `HTTPS_PROXY`，客户端遵循 httpx 环境代理规则。不要在错误日志中打印代理凭据。

影子记录位于 LangGraph 会话状态的 `intent_classifier_evidence`，包含实际模型版本、分类分数、原理解意图及一致性标记，或安全错误类别。失败不改变原理解结果。第一版未添加前端查看页面，也未启用混合快速路径。

第一版 `timeout_seconds` 是 httpx 各网络阶段的超时，而不是严格的总墙钟时间；默认单次请求不重试。影子采样在原理解之后同步执行，会增加响应等待时间。严格总截止与并行评估需在后续阶段结合现有运行时实现，不能将此配置当成端到端延迟保证。

## 本次实现验证

新增协议和图节点回归以及现有纯函数架构测试共 61 项通过；包含助手、记忆、事件和配置 API 的相关回归共 96 项通过、2 项失败。两项失败为现有消息排序与只读查询状态用例，切回 HEAD 原图文件后同样复现，未修改其业务逻辑。相关 Python 文件 Ruff 检查通过。

通过当前 Windows Python/httpx 客户端进行一次真实影子请求：`jev-latest` 返回 `jev-1.13.0`，主意图 `job_search`、分类 confidence 1.0、禁止发送 Noul 0.97，耗时约 1,022 毫秒。多动作 Noul 为 0.52，说明该信号尚需针对否定动作样本评测；当前仅记录，不能据此自动规划。密钥仅注入测试进程环境，未持久化。
